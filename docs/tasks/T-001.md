# T-001: Close two check-then-act races (order flows, refresh token rotation)

Status: agreed · Branch: task/T-001-race-locks · Risk: high (stock math and auth)

## What we're building
Two requests arriving at the same moment can no longer both pass the same check. An order changes stock exactly once even when two people click Cancel or Reserve together. A refresh token can be used once, even when the same token is sent twice at the same moment.

## Done when
Each point is something you can see working, and the test that proves it.
- AC-1: two cancels at once on a RESERVED order: both answer 200 with CANCELLED, stock goes back up exactly once (test: `tests/test_concurrency.py::test_concurrent_cancel_restocks_once`)
- AC-2: two reserves at once on a NEW order: both answer 200 with RESERVED, stock goes down exactly once (test: `tests/test_concurrency.py::test_concurrent_reserve_takes_stock_once`)
- AC-3: two refreshes at once with the same refresh token: one 200, one 401 (test: `tests/test_concurrency.py::test_concurrent_refresh_one_wins`)
- AC-4: every order flow (reserve, retry reserve, start pick, confirm pick, ship, cancel, integration reserve, integration release) reads the order through a new `get_order_for_update` (`SELECT ... FOR UPDATE` on the order row) before checking status; the stock-failure branches that re-read the order use it too. Both product locks get `.order_by(Product.id)`, so locks are always taken in the same order. (test: the full existing suite stays green in CI)
- AC-5: `rotate_refresh_token` does one `UPDATE ... SET revoked_at = now WHERE token_hash = ? AND revoked_at IS NULL AND expires_at > now RETURNING user_id`. 0 rows means 401, with the same three messages as today (D-001). (test: AC-3, plus the existing auth tests)

Evidence: these tests use the database, so they run only in CI, never locally (Databases in CLAUDE.md). The evidence is the CI run on this branch (`gh run list --branch task/T-001-race-locks`), so the branch is pushed before /task-review.
